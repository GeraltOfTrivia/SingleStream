## Dossier 1: Gemma-4 12B QUASAR W4A16-G64 First Qualification (Target-Only)

### Model and configuration

* Target Model: `gemma-4-12B-it-QUASAR-W4A16-G64` — `QUASAR-QAT` native int4 QAT export of `google/gemma-4-12B-it`: 328 decoder linears int4 symmetric group-64 (4.25 quantized bpw), everything else bf16, 0.034 KL to BF16 (23 % lower than Google's official W4A16 QAT g32); dense 48 layers (40 sliding-window-1024 + 8 full-attention), hidden 3,840, native 262,144 context, tied embedding 2.01 GiB (UVA-offloaded to host pinned RAM), no integrated MTP head — the drafter is necessarily external
* Drafter Model: `gemma-4-12B-it-qat-assistant-w4a16-ct` — RTN int4 group-128 (Marlin) assistant quantized from `google/gemma-4-12B-it-qat-q4_0-unquantized-assistant`; 4-layer draft backbone (hidden 1,024), 2,048 centroids / top-32, `backbone_hidden_size` 3,840 == target hidden (the proposer wires cross-model KV sharing natively), 0.59 GiB; vLLM 0.32 rewrites `gemma4_unified_assistant` → `Gemma4MTPModel` with `n_predict=1` hardcoded (one draft token per drafter forward — the draft depth $k$ is a chained re-forward of the same head via `num_speculative_tokens`, k=1/2/3 verified in this campaign) and `num_kv_shared_layers` force-zeroed. The int4 checkpoint is boot-blocked on this stack (quantized `post_projection` loader gap — Finding 2); the drafter arm ran the BF16 producer reference `gemma-4-12B-it-qat-assistant-bf16` (the exact producer model used for the int4 preparation)
* Hardware: NVIDIA RTX 2000 Ada Generation (16 GB, SM89, 70 W).

### Evaluation conditions

- Target-only is measured before assistant speculation. Both FP8 and NVFP4 KV are attempted; the FP8 model-specific boot boundary is described below.
- The target-only arm uses float16 computation; speculative arms use BF16. The difference is part of the comparison.
- The initial reasoning threshold is 180/200; the standing threshold remains 190/200.
- The external assistant uses the Gemma MTP method. Draft depth is the number of chained head forwards; it is not DFlash2 block drafting.

### FP8 KV Kernel Boundary on SM89 (Campaign Finding 1)

The `fp8` arm cannot boot on this model on SM89 — a deterministic FlashInfer kernel-support boundary, not a transient failure:

* During CUDA-graph profiling (`profile_cudagraph_memory` → capture warmup), the FlashInfer FA2 prefill module generation for the head_dim-512 full-attention layers + fp8 (e4m3) KV requests nvcc flags restricted to `supported_major_versions = [10, 11, 12]` (SM100/110/120). The gate (`_fa2_head_dim_nvcc_flags`) fires only for `head_dim > 256` with one-byte KV, and the SM8 exception applies to NVFP4 KV only (`allow_nvfp4_sm8_large_head`). SM89 is major 8, so module generation raises `RuntimeError: No supported CUDA architectures found for major versions [10, 11, 12]` → EngineCore start fails → the arm is boot-blocked (`Boot failed; no retries`).
* The NVFP4 KV arm boots clean: the FlashInfer large-head NVFP4 path (`allow_nvfp4_sm8_large_head`) compiles both the head_dim-256 (sliding-window) and head_dim-512 (full-attention) prefill modules for SM89.
* Gemma-4-12B's dual head geometry (40 sliding-window layers at head_dim 256, 8 full-attention layers at head_dim 512) is what pushes fp8 past the SM89 boundary; head_dim 256 sits exactly on the other side of the `> 256` gate. That is why the Qwen3.8-27B runs (head_dim 256 everywhere, `qwen3_5` geometry) ran fp8 KV fine on this card  while Gemma-4-12B cannot — only its 512-head full-attention prefill module is SM100+ for one-byte KV.
* Consequence: for this checkpoint the FP8 versus NVFP4 comparison collapses to NVFP4-only on the 16 GB Ada card; the `fp8` arm is recorded NOT APPLICABLE (kernel boundary) and the drafter runs are `nvfp4`-only.

### Drafter (int4) Boot Blocker — Campaign Finding 2

The int4 drafter `gemma-4-12B-it-qat-assistant-w4a16-ct` cannot boot on the canonical stack :

* During Gemma4MTP drafter load, the quantized loader requests plain `model.post_projection.weight`; the int4 checkpoint holds that layer only in Marlin-packed form (`weight_packed` / `weight_scale` / `weight_shape`), and `Gemma4MTP`'s quantized `post_projection` mapping is absent → `ValueError: There is no module or parameter named 'model.post_projection.weight' in Gemma4MTP` → EngineCore start failure.
* The 24GB-moe NVFP4 (modelopt) 26B assistant did not hit this gap — it is specific to the int4 compressed-tensors packing of `post_projection` on this stack.
* Consequence: the drafter role was tested with the BF16 producer reference `google/gemma-4-12B-it-qat-q4_0-unquantized-assistant` (local copy `gemma-4-12B-it-qat-assistant-bf16` — the exact producer model used for the int4 preparation, so the TG verdict remains meaningful for the drafter *model*). The int4 checkpoint is recorded as boot-blocked (loader gap); the tested runtime lacks the required quantized projection mapping.

## Dossier 2: Gemma-4 12B Drafter Arm (k1 to k3) and k3 Extended Battery

### Results — Drafter Arm (BF16 Assistant, Smoke, TG Verdict + Draft-Depth Sweep)

The assistant-depth sweep uses the Gemma MTP method with one, two, and three chained draft proposals. These are speed screens rather than three complete qualification batteries.

* All $k$ share the boot profile: model + drafter 8.54 GiB, pool 870,533 tokens (the Gemma4MTP drafter is Q-only and writes no new KV slots), admitted 262,144; peak GPU 15,328–15,548 MiB. `kld-distribution` record-only in each run (5 prompts / 938 positions).
* Mechanics: with $k>1$, vLLM chains the same 4-layer head $k$ times (`speculative.py:1381` warning: *"Enabling num_speculative_tokens > 1 will run multiple times of forward on same MTP layer, which may result in lower acceptance rate"* — present in both sweep logs). Per-position acceptance decays (80.6 → 70.5 → 61.1 %) while the acceptance length grows (1.81 → 2.83), so net throughput keeps rising through $k=3$; higher depths were not tested in the sweep.

Verdict: the MTP drafter improves decode on the 70 W Ada card at every tested draft depth — $k=1$ +50.4/+48.5 %, $k=2$ +78.4/+76.5 %, $k=3$ +97.3/+95.6 % over target-only (25.03/24.91). `n_predict=1` only means one draft token per forward; the depth $k$ is a chained re-forward that the `Gemma4MTP` speculator supports (verified above). The speed sweep is not three separate qualification batteries. The separate k3 extended result is reported below; k4 was not tested.

Campaign Finding 3 — near-max (261 K) mid-context retrieval loss. `deep-ctx-261120` (260,608-token prompt: 3 NIAH passcode needles at depths 0.05/0.50/0.95 + 6 leader/budget facts at 0.10…0.90, single greedy 512-token generation) retrieved the 0.05 passcode and the 0.10 / 0.25 / 0.75 facts, but missed the 0.40 / 0.60 / 0.90 facts and hallucinated the missing values with plausible names/numbers that do not exist in the prompt (Amber → Julian/31 instead of Mira/37; Willow → Elena/27 instead of Elin/19). 4 of 13 expected tokens missing (`Mira`, `37`, `28`, `Elin`). This is the model's own maximum context (262,144), where 40 of 48 layers are sliding-window-1024 — long-range retrieval rides on the 8 full-attention layers only, so the observed failure needs the target-only control below to assess drafter involvement.
Target-only control (2026-10-26). A bare target-only / prefix caching OFF cold 261,120 prefill (int4 target, NVFP4 KV, admission 262,144, pool 1,034,045) reproduces the identical failure: same missing set (`Mira`, `37`, `28`, `Elin`) and byte-identical confabulated values (Julian/31, Elena/27, Elm→19) with zero speculation or cache involvement. The same failure without speculation or prefix caching shows that neither is necessary for the observation. An equivalent FP8 control is unavailable on this card, so model architecture and KV precision remain unisolated.

Campaign Finding 4 — cold/warm greedy parity fails with k3. `prefix-cache-32k` verifies the cold-miss → warm-hit leg: the warm hit reports (43.18× speedup, 32,704 tokens served from cache) but cold and warm greedy outputs diverge from the first token (`text_parity: false`). The mismatch is observed with k3; its precise numerical cause is not isolated; the test records execution as `PASS` (execution-only gate) — the record-level `passed: false` indicates failed output parity.

## Dossier 3: Qwen3.8-27B NVFP4 + MTP-3 0.32 Qualification

### Motivation & Setup

Qualification of the prepared Qwen3.8-27B W4A16 target with integrated MTP-3 and NVFP4 KV.

Configuration: `Qwen3.8-27B-W4A16-AutoRound-fast` (int4, unquantized MTP head), FlashInfer + NVFP4 KV, built-in MTP-3 ($k=3$), prefix caching OFF, $C=1$.

### Results — Qualification Battery (PASS)

* Boot: auto-fit admission 41,216 tokens (pool 42,246; 1.12 GiB KV + 12.7 GiB model; peak 15,902 MiB of 16 GB).
* Correctness smoke, KLD (5 prompts, 946 positions): PASS.
* TG: greedy 33.92 tok/s (TTFT 317.7 ms) @ MTP acceptance 53.4 % / mean draft length 2.6; instruct 30.57 tok/s @ 44.9 %.
* GSM8K-200 greedy: 193/200 PASS (standing $\ge 190/200$ gate).
* PPL: en 10.79, de 10.19, el 5.44, code 3.69.
* Prefill ladder: pp-1024 cold 672.4 tok/s (warm = cold — prefix OFF by design, speedup 1.0); pp-16384 uncached 615.7 tok/s; pp-65536 NOT APPLICABLE (admission 41,216). Occupied-1024 PASS; 65,536/131,072 rungs skip above admission.

### Verdict

The Qwen configuration scores 193/200 and admits 41,216 tokens. The larger Gemma context admission is a separate capacity result, with its near-limit retrieval failure retained above.
